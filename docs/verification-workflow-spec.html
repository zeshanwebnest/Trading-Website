This document specifies how admin review should work. None of the admin-facing half exists in the codebase today — this is the blueprint for it, not a manual for something already running.

What exists vs. what this describes

The Open Account form and Client Dashboard built so far are front-end only, by design. Submitted data is saved with localStorage.setItem('vaultEasyAccount', …) — inside that one visitor's own browser, never sent anywhere. There is no server, no database, and no admin login. The dashboard's status tracker is hardcoded to show Submitted as done and Under Review as current; nothing anywhere can currently move it to Verified, because no code exists to move it. An admin can't "view submitted requests" today because there's no shared place they land — each one is stranded on a different applicant's device.

Everything from here down describes the system as it needs to be built. Section 3 covers the infrastructure that has to exist before any of it is real.

Target behavior

The status lifecycle

Four states, one direction of travel except for the resubmit loop after a rejection.

Submitted
Applicant finishes the form
Under Review
Sitting in the admin queue
Verified
Admin approved
Rejected
Admin declined, reason given

A Rejected applicant can edit and resubmit from their dashboard, which returns them to Under Review — not back to square one, and not auto-approved.

Before any of this can be built

What has to exist first

Four pieces of infrastructure the current front-end prototype doesn't have. All four block everything described below.

A real database

Submissions currently live in one browser's localStorage. They need a server-side table (or collection) keyed by applicant, so an admin — on a different machine entirely — can see them.

Encrypted document storage

CNIC images and proof-of-address files need to land somewhere encrypted at rest, with access limited to the applicant and admin staff — not a public bucket, not inline in the database.

A separate admin login

Admin staff need their own authenticated accounts, distinct from client accounts, so "who is allowed to approve applications" is a real, checkable identity rather than a guess.

Role-based permissions

A flag on the account record — role: 'client' | 'admin' — that every API endpoint checks before doing anything sensitive. This is what actually makes approval admin-only; see Section 7.

Step 2 of 3 — Reviewing an application

The review screen

One consolidated view per applicant — this is "where all documents and information are displayed." It mirrors the five steps of the Open Account form, so a reviewer sees data in the same shape the applicant entered it.

1

Personal & identity summary

Name, contact details, and CNIC number rendered as text — plus the CNIC front and back images displayed inline, full size, click-to-zoom. This is the first cross-check: does the photo match the typed number and the applicant's stated name?

2

KYC profile

Occupation, source of funds, income bracket, trading experience, and the Politically Exposed Person declaration — flagged visually if the applicant answered Yes, since that answer typically triggers additional review in most brokerages' compliance policy.

3

Bank details

Bank name, account title, and account number — with the account title checked against the applicant's stated full name, since a mismatch is one of the more common reasons to reject or ask for clarification.

4

Supporting documents

Proof of address and any additional uploaded file, previewed inline (images) or linked (PDFs) — never a bare filename with no way to actually look at it.

Step 3 of 3 — Making the call

Approving or rejecting

Two actions live at the bottom of the review screen. Both require the reviewer to be signed in as an admin — see Section 7 for how that's actually enforced, not just displayed.

Approve

Sets status: "verified", stamps reviewedBy and reviewedAt, and is the only thing that ever changes an account to Verified. The applicant's dashboard reflects the new status the next time it loads — no separate sync step, since it's reading the same server record the admin just wrote.

Reject

Requires a short reason (e.g. "CNIC image unreadable — please re-upload"). Sets status: "rejected" and surfaces that reason on the applicant's dashboard, along with an option to edit the affected fields and resubmit — which returns the account to Under Review, not back to a blank form.

Either action should also queue an email to the applicant. A status change nobody tells them about isn't meaningfully different from no status change at all.

The part that has to be right

Why users can't self-verify

Hiding the Approve button from regular users is not what makes this admin-only. Enforcement has to happen on the server, not in the browser.

Right now, and in any future version, a client's own browser is not a trusted environment — anyone can open dev tools and call an API directly, bypassing whatever buttons the interface does or doesn't show. So the rule "only admins can verify" has to be checked at the one point a user can't edit: the server, on every single request.

// Every status-changing request checks the caller's role server-side —
// never trusts a role or permission sent from the browser itself.
async function approveApplication(request) {
  const session = await getSession(request);

  if (!session || session.role !== 'admin') {
    return respond(403, 'Forbidden');
  }

  // Only reachable past this line if the server itself confirmed
  // the caller is a signed-in admin — not because a button was visible.
  await db.applications.update(request.applicationId, {
    status: 'verified',
    reviewedBy: session.userId,
    reviewedAt: new Date(),
  });
}

Three things fall out of that one rule:

  • A client account, however it's manipulated, has no code path that can ever set its own status to verified.
  • Admin sessions are separate logins with their own credentials — not a checkbox on a normal user account.
  • Every approval and rejection is logged with which admin made the call, so the decision is attributable, not anonymous.

Status field reference

The fields a real backend needs to add to today's vaultEasyAccount record once it's server-side.

status: 'submitted' | 'under_review' | 'verified' | 'rejected'
reviewedBy: string | null       // admin user id, set on approve/reject
reviewedAt: string | null       // ISO timestamp, set on approve/reject
rejectionReason: string | null  // required when status is 'rejected'
